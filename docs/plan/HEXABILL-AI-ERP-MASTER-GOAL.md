## PHASE 3 — AI control plane + secure text assistant (P2)
### 3A. Architecture: NO generic DB-connected chatbot
- Build server-side AI Gateway/Coordinator with typed `IAiProvider` adapters and `IToolRegistry`/policy authorizer. User -> authenticated tenant/session -> capability/feature/usage gate -> intent -> authorized tool retrieval -> minimal relevant facts -> model -> answer with date range, currency, source record links, timestamps and caveats. Never model-generated SQL or fabricated financial figures.
- Classify operations `read`, `draft`, `confirm`, `post`. Read-only by default. Strict tool allowlist and JSON schema + validation. Tool calls scoped to tenant/user/role and optionally branch/route. Rate-limit and paginate. Never treat any model response as authority to change accounting data.
- Tool registry examples: `GetSalesSummary`, `GetCustomerBalance`, `FindCustomer`, `FindProductSku`, `GetLowStock`, `GetOutstandingInvoices`, `GetPurchaseSummary`, `GetExpenseSummary`, `GetDailyClosePreview`, `GetStaffActivitySummary`, `GetRouteProgress`, `GetVATSummary`. Bind to actual existing backend services. Invoice draft creation later uses preview->human confirm->server revalidate->idempotent post.
- Prefer existing database query/service access for structured ERP data; vector index/RAG ONLY for help docs, terms, user manuals and permitted unstructured files, tenant-scoped by metadata AND query filters. Reindex on ACL changes, avoid stale references.
- Deterministic tools for balances, taxes, ledger, stock, rounding and date arithmetic; model for intent detection, explanation and multilingual presentation. Clear citations/source links and 'data as of'.

### 3B. Model/provider gateway and policies
- One registry for direct Gemini, direct Groq, OpenRouter and optional verified OmniRouter plus selected paid model providers. Discover model IDs, statuses, modality, function calling, JSON schema, supported locale, privacy/data retention, prices, limits, request concurrency, health and regional data restrictions dynamically; pin tested models per task.
- OpenCode is a coding agent/tool, not an LLM API for production app inference; no hidden link between Claude subscription and ERP inference. Don't treat gateways as unlimited free tokens. Gemini free usage conditions (including data use), OpenRouter free daily caps, Groq account-model rate limits, LiveKit transport and agent allowance, OmniRouter prepaid terms must be checked before enabling customer data.
- Task-based selection with a capability+policy+budget gate: deterministic no-model paths first; low-cost text model for classification/summary; stronger paid model only when approved for sensitive/complex tasks; voice-specific route for validated language. Free->paid fallback requires explicit SuperAdmin or tenant policy and cap, and user-visible degradation/failure semantics. NEVER rotate keys to circumvent rate limits or use multiple free accounts to evade terms.
- Health/circuit breaker, timeouts, exponential backoff only for idempotent reads, result caching tenant+permission+locale+date scoped, small context budgets, streaming, max response size, prompt/model versions, cost forecasting and hard caps. Provider choice defaults must not depend only on price; test accuracy and Malayalam/Hindi/Arabic reliability.
- Provider error states: 401 invalid/revoked key, 402 balance, 403 forbidden/data-policy, 404 disabled model, 408 timeout, 429 rate limit, 5xx outage, schema/tool failure, exceeded tenant budget, cancellation. Fail closed on no approved provider. Text/manual workflow remains available even if all AI providers fail.

### 3C. SuperAdmin AI control center (server-enforced)
- Provider registry table: provider name, adapter endpoint allowlisted, key secret reference, enabled/tested, permitted purposes, allowed models, verified pricing/time, storage/region/data processing, health, quotas, key rotation audit.
- Model controls: per-task, per-tenant and global allow/deny lists; default/backup model, reasoning/latency tier, preview/production flag, text vs voice, fallback policy; one-click disable AI globally or by tenant; staff/owner configurable seat quotas if permitted.
- Usage dashboard: tenant/user aggregate counts, tokens, voice minutes (STT/TTS/realtime separated), request errors/429, latency, estimated USD/AED, credits remaining if provider API supports it, usage trends, daily/monthly cap, cost-per-task, model health, routing decisions; accessible only to authorized SuperAdmin. Owners see own tenant summary, staff limited as configured.
- Email/notification alerts: spend thresholds 50/80/100%, repeated failures, key invalid, suspicious cross-tenant/unauthorized tool attempts, unusual traffic, voice-minute spikes, approaching budget, low stock / daily close discrepancy if opted-in. Deduplicate/escalate alerts; no plaintext customer data or prompts in emails; test owner/admin unsubscribe/consent where appropriate.
- No arbitrary provider URL from UI unless validated/allowlisted and SSRF-safe. SuperAdmin keys are secrets not exposed in browser or LLM context. Rotation without outage; test connection with synthetic prompt only. Strict audit.
- Tenant subscription/feature controls: AI on/off, text vs voice, premium permission, staff seat limits, tenant/day/month budgets, retention settings, region, model allowlist; disabled feature removes UI and rejects API calls.

## PHASE 4 — Multilingual voice (Malayalam/English/Hindi/Arabic first) (P2→P3)
### 4A. Two modes, both with reliable text fallback
- **MVP push-to-talk:** browser mic permission -> audio capture -> approved STT (test direct Groq Whisper or other language-verified engine) -> visible transcript editable -> existing tenant-safe AI tools -> text response -> optional TTS. Cheap, debuggable and ideal for mobile/low connectivity. When confidence low, ask to confirm transcript, do not write business data.
- **Phase 2 continuous two-way voice:** LiveKit Agents/WebRTC (managed free-tier for prototype or self-host carefully), with either Gemini Live realtime model or streaming STT->LLM->TTS cascade. LiveKit is transport/orchestration, not unlimited free speech inference. Do not claim a free voice model supports Malayalam until smoke-tested end to end. Agent service requires authenticated short-lived server-minted room/token scoped to user+tenant, quotas, role, agent config; no browser API keys.
- Languages: detect or select `ml`, `en`, `hi`, `ar` initially; mixed Malayalam-English, Hindi-English, Arabic-English, names/SKU, numeral and currency readback; other languages only after verified per STT, LLM, TTS and locale stack. Keep localized text labels and RTL where applicable. 'Any country language' is a roadmap, not an unsupported promise.
- Voice UX: push-to-talk icon, mic-on badge, waveform, live caption, language selector/auto, interrupt, cancel, end session, mute, text/voice toggle, repeat/rephrase, listen/transcript privacy, readable costs/limit indicator, visually distinct preview and confirmation. Test accent, noise, Bluetooth, unsupported device, mic denied, audio route changes, interruptions, silence, background tab, network roaming, concurrent sessions, token expiry, speech profanity/prompt injection, invalid numbers, currency spoken ambiguously.
- NEVER auto-post invoices, pay suppliers, change prices, close cash, export sensitive data or update payroll from voice. Structured summary reads allowed. Draft preview with source record match/ambiguities and explicit user confirmation plus server validation and idempotency.
- Audio, transcript and conversation retention configurable and minimal, default not recorded unless necessary/consented; disclose provider processing and opt-out; purge by tenant, ensure storage region/transport. Log only metadata unless approved. Stop work on tenant suspension or permission revocation.
- Latency objectives must be measured on real UAE/India devices (including Malayalam code-switching), not invented. Instrument turn-start->first transcript->first response/audio, quality and cost per voice-minute. Set fallback to text whenever streaming quality/cost is inadequate.

## PHASE 6 — Forecasting / ML with controlled feedback loop (P3)
- Only after sufficient clean tenant history and data quality. Start baseline (moving avg, seasonal naive); consider gradient boosted trees/time-series models for demand/stock reordering, payment-delay risk, customer inactivity, cash-flow patterns and route ETA. No invented accuracy. Separate model per tenant or privacy-safe shared model with documented approval and leakage controls; tenant-specific features and evaluation.
- Time-based splits; backtest vs baseline, MAE/WAPE and business cost (stockout vs overstock) depending on task; drift and data freshness, low-volume tenant fallbacks, holidays seasonality, frozen goods shelf life and inventory expiry where records exist.
- Feedback is explicit: recommendation shown -> accepted/rejected -> business outcome -> evaluate -> scheduled retrain only after offline validation/versioning/human approval; never live online training on raw invoice fields.
- Predictions are advisory. NEVER auto-overwrite customer last price, VAT, sales records or financial totals. Store prediction timestamp, model version, source window, confidence/interval where calibrated.
